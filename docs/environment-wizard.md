# Environment wizard: automatic FSLogix storage setup

Issue 32, plan section 1b (phase 3). Code: `Modules\AVDTune.Environment.psm1`, page `AVDTune-Environment.ps1` with `UI\AVDTune.Environment.xaml`. Fake: `Tests\Fakes\FakeEnvArm.ps1`. Check: `Tests\Check-Environment.ps1`. The first-run questions themselves (`AVDTune.Start.psm1`, `docs\start-sequence.md`) are unchanged; this page takes their answers (identity model, endpoint, DNS) and plans the Azure side.

## What it does

1. **Identity model** (`Get-AVDTuneEnvIdentityModel`, from `AzureFilesAuth` of the first-run answers):

   | Model | ARM value | AVDTune | By hand (listed as steps, with the reason) |
   |---|---|---|---|
   | Microsoft Entra Kerberos (cloud-only or synchronized) | `AADKERB` | sets it on the account; hybrid identities: domain name and GUID | admin consent of the storage account app, Conditional Access exclusion (MFA gives error 1327), the cloud-only groups tag in the app manifest (cloud-only identities only) |
   | Microsoft Entra Domain Services | `AADDS` | sets it on the account | hosts must be joined to the managed domain |
   | AD DS | `AD` | nothing yet | computer account, Kerberos key, SPN, `activeDirectoryProperties` (no LDAP write path exists; issue 32, question 1) |

2. **Plan** (`Get-AVDTuneEnvPlan`): reads every resource with GET and compares it with the wish. Steps, in this order: storage account, SMB settings, share, private DNS zone, VNet link, private endpoint, DNS zone group, identity source, role assignment for the user group, role assignment for the admin group; then the deferred steps NTFS ACL, FSLogix on the master and test. Each step is Create, Update, None, Manual, Blocked or Deferred, carries the exact request body, the Learn source and whether Learn states it. The plan has a hash over what would be sent. Before it, the rights are checked (`Microsoft.Authorization/permissions` of the resource group: storage, network, DNS, `roleAssignments/write`, `subnets/join/action`); a missing action blocks the plan and names the action and why it is needed. A Contributor, for example, cannot write role assignments. The role assignments of the share are read over all pages: a `nextLink` is followed only on `management.azure.com` and only as a subscription path (the rules of the polling), at most 20 pages; any other link or a failed page gives a warning and is not followed (Azure answers an existing assignment at the write).
3. **Create** (`Invoke-AVDTuneEnvApply`): needs the open snapshot gate. The plan is built again and must have the hash the administrator confirmed; otherwise nothing is written. Resource by resource; an asynchronous operation is awaited (`Azure-AsyncOperation`, `Location`, `Retry-After`; without headers the resource is polled); first failure stops, the rest is Skipped. Existing resources are never replaced and a create is a create: one more GET right before it, and when the resource exists now nothing is sent and the run stops (`If-None-Match: *` would be the server side form; the ARM adapter has no request headers yet). After the create the creation time or guid is read and written to the journal. **Remaining window:** the GET before the create and the PUT are two requests, and the server side form (`If-None-Match: *`) is not available, so a resource created by someone else in between would be overwritten by the PUT. AVDTune therefore reads the resource after the PUT: when its creation time (`systemData.createdAt`, `creationTime` or `createdOn`) is older than the start of AVDTune's own request, the resource existed before it. It is then marked foreign in the journal (`Identity.Foreign = true`), is never deleted by the undo, and the run ends with a warning (step Failed, the rest Skipped). The comparison uses the clock of this computer against the one of Azure: a clock that runs ahead can mark a new resource as foreign (it is then only kept, the safe direction), a clock that runs behind can hide a resource that was made a split second before. If the identity cannot be read after the create (or the resource carries none), the journal says so (`IdentityMissing`, with the reason) and the undo keeps the resource. An existing account is only made stricter: secure transfer on, no blob public access, TLS 1.0/1.1 to 1.2 (levels compared in order, TLS 1.3 stays, unknown values stay); public network access is never switched on or off on an existing account: with a private endpoint and public access on, a manual step and a warning; a public account with firewall default Allow gets a warning. The old values are recorded. A new account has shared key access off (identity based access only; the note names the portal setting for the emergency access). Kind and SKU of an existing account are never changed (a Standard account only gets the "not recommended for FSLogix" warning).
4. **Undo** (`Get-AVDTuneEnvUndoPlan`, `Invoke-AVDTuneEnvUndo`): works only from the journal `config\azure-setup.json`, and the journal is input, not trust: an entry counts only for a resource of its own type (the rule of the allowlist, not a flag in the file) in the subscription, resource group and storage account (private endpoint name) of its own run; the recorded old values are reduced to the keys and enum values the setup can write. A create entry is deleted only if its status is Done and an identity was recorded; entries without an identity (also empty), with the status Failed or Started, or marked foreign are only kept, with the reason. A resource is deleted only if it still exists, is the one that was created (creation time and guid recorded at the create and compared now: a resource deleted and made again under the same name is not touched) and (where Azure allows tags) carries `CreatedWith=AVDTune`. Reverse order. A share is deleted only when `Test-AVDTuneEnvShareEmpty` proves it empty over the data plane (storage token): `$true` only for a 2xx answer, parsed XML, no directory and no file entry and no `NextMarker`; 403, no connection, bad XML or a marker mean "cannot prove it" and the share stays. A storage account is deleted only when ARM lists exactly the shares AVDTune created and each of them is verified empty (per share and per account, two runs do not influence each other). Both checks run again right before the DELETE. The private DNS zone and its VNet link both stay when the zone holds other record sets: the record sets of the zone are counted at the plan, and again right before the delete of the zone and of the link; the own A records are counted by the zone groups that exist now (a GET each, matched to the zone), not by journal entries. Updates of an existing account are restored from the recorded values, except what would lower the security: https only off, public blob access on or TLS below 1.2 is shown in the undo plan as kept (with the values) and not written back; `publicNetworkAccess` is not in the recorded values at all (the setup never changes it); settings of an account that is deleted are covered by that. A new confirmation of the undo plan hash is needed.
5. **Master and test**: `Set-AVDTuneEnvMaster` writes `Enabled=1` and `VHDLocations` through the existing FSLogix settings steps (gate, run record, change log, undo of the FSLogix page) and, for Entra Kerberos, `CloudKerberosTicketRetrievalEnabled=1` (`HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Kerberos\Parameters`, Learn: Entra Kerberos, registry key tab). `Get-AVDTuneEnvAclDiff` shows the NTFS diff with the existing ACL logic (group object IDs become `S-1-12-1-...`); setting it stays `Set-AVDTuneStorageRootAcl` with its confirmed hash. `Invoke-AVDTuneEnvVerify` runs the existing storage check for the new share.

## Rules this code keeps (docs\security-checklist.md)

| Point | How |
|---|---|
| Path segments from data validated | Names go through `Test-AVDTuneEnvSpec` (`[A-Za-z0-9._()-]`, storage and share name rules, GUIDs); `Assert-AVDTuneEnvArmPath` checks again at the request: one `?`, no `#`, no `..`, only `api-version` for writes |
| ARM only through the adapter, allowlist | Every request goes through `New-AVDTuneArmAdapter` (host fixed, no redirects). This module allows PUT, PATCH, DELETE only for eight resource types with their api version; POST (listKeys, regenerateKey) never |
| Tokens only to their host, no redirects followed | Polling links are absolute URLs: only `https://management.azure.com/subscriptions/...` is followed (`ConvertTo-AVDTuneArmPath`), anything else fails the step |
| Role assignments | The writer checks the body of every role assignment: one of the two share role definitions of this subscription, principal type Group, a GUID. The plan shows the display name of the group when the administrator typed it (no Graph read, so AVDTune does not look it up) |
| Secrets | The module has no key call, no HTTP client; the token is a parameter, never in the plan, journal, change log, run record or a message (checked by scanning the files) |
| Write gate and LastChange | Apply and undo throw without the gate and need the confirmed plan hash. Azure resources do not set `LastChange` (not in the OS disk snapshot; their way back is the journal undo, user decision, issue 32); the master part (`Set-AVDTuneEnvMaster`: Enabled, VHDLocations, CloudKerberosTicketRetrievalEnabled) sets it before writing, also when a write fails. Change log entries of Azure steps have the category Azure, which `Get-AVDTuneLastChange` ignores |
| Change log and undo | One entry per step (also for undo); undo works only on what the journal says AVDTune created, and never deletes data |
| Crash safety | The journal is written before and after every write (`Started`, `Done`, `Failed`) |
| Data is data | A journal entry that names another resource type produces no step and no request |

## Not verified (to try on a test tenant)

- Whether every resource type carries a creation time or guid that the identity can use (`systemData.createdAt`, `creationTime`, `createdOn`, `resourceGuid`, `internalId`). A type without one is never deleted by the undo (kept, reason in the plan); this may be the case for file shares.
- The request shapes are written from the REST reference and not tried against Azure: storage account (api 2024-01-01, `networkAcls`, `defaultToOAuthAuthentication`), file service SMB settings by PUT (whether properties that are not sent stay unchanged is not stated; only the `smb` block is sent), share (`accessTier` Premium), private endpoint and zone group (api 2023-11-01), private DNS zone and link (2020-06-01), role assignments (2022-04-01). The fake gives the answers Azure gave in earlier work (201/202, `Azure-AsyncOperation` for network and DNS, `Location` for the storage account, 400, 403, 409), but it is a fake.
- Premium IOPS and throughput (3000 + 1 per GiB, 100 + 0.1 MiB/s per GiB) are the formula of the Learn billing page and shown as an estimate.
- Role propagation after the role assignments can take minutes; the NTFS step is separate for that reason.
- `LoadCredKeyFromProfile` from plan section 1b is not on the Entra Kerberos page of Learn and is not set.
- The page runs plan, create and undo on the window thread behind a task in the bar (like the changes of the FSLogix page): the window waits while Azure works. A background runspace is a follow-up.

## SharePoint site of the environment: the role write (issue 96)

Code: `Modules\AVDTune.SiteAccess.psm1`, the last card of the Environment page, `Tests\Check-SharePoint.ps1` (fake sign-in and Graph of `Tests\Fakes\FakeServices.ps1`). The uploads of issue 89 (change log, software list, environment document) use the Sites token of the sign-in, which only holds `Sites.Selected`. That permission gives no access alone: the app registration needs a role on the one site (`POST /sites/{id}/permissions`). Until now a 403 only showed a hint.

1. **Plan** (`Get-AVDTuneSiteAccessPlan`, pure): the site of `config\sharepoint.json`, AVDTune's own app registration (client ID and tenant of the sign-in, never Microsoft's setup app), the role `write`, the exact request and a hash over site, registration, tenant and role. The confirmation names site, role and registration and says what the sign-in leaves behind.
2. **Grant** (`Grant-AVDTuneSiteAccess`): not after the finish, snapshot gate open, the plan is built again and must have the confirmed hash. A second, short sign-in through Microsoft's public client "Microsoft Graph Command Line Tools" with `Sites.FullControl.All` at the tenant of the environment; the token is checked (Graph audience, tenant, permission), used for this step and dropped in `finally`. Requests go through the Graph member of the sign-in adapter (`https://graph.microsoft.com/v1.0` only, no redirects). The site id is validated against the host of the site address. If the registration already holds write (or manage, fullcontrol, owner) nothing is sent and nothing recorded. Otherwise: journal `config\sharepoint-access.json` (`Started`), POST, read back (the new permission must name exactly this registration and the role), journal (`Done` with the permission id, or `Failed`), change log (category Azure). No `LastChange`: the site is not part of the master (clarification of issue 32).
3. **Undo** (`Get-AVDTuneSiteAccessUndoPlan`, `Revoke-AVDTuneSiteAccess`): only from the journal, which is input and not trust (site id of the host of its own site address, client ID a GUID and not the setup app, role write, permission id of known characters, `Undone` only as a real boolean). Only a `Done` grant with its permission id is removed; an interrupted or failed one is kept with the reason. The permission is read again right before the DELETE and removed only when it still names exactly that registration; one that is gone is marked as taken back. The adapter allows DELETE for `/v1.0/sites/<id>/permissions/<id>` and nothing else.
4. **Readiness row** `hy.sharepoint-access` (`Get-AVDTuneSiteAccessState`, one GET of the site with the Sites token): only when a site is set. 401/403 = yellow (the role is missing); granted by AVDTune and readable = green; readable without an own grant = info (whether the role allows writing cannot be read with `Sites.Selected`); not signed in or not reachable = info, not an open item.

What stays in the tenant: the consent of the administrator for `Sites.FullControl.All` on "Microsoft Graph Command Line Tools". AVDTune does not remove it (that would need `DelegatedPermissionGrant.ReadWrite.All` for this step); the confirmation and the card say where to remove it.

Not verified against a real tenant: the request shapes (site permissions of the Graph reference, as in PackTune's package store), the characters of a permission id (an id with other characters is recorded as failed and never removed by AVDTune), and whether a site owner without a SharePoint role may grant.
