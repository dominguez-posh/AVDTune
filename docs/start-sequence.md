# Start sequence

Nothing changes the master before these four stages on the Overview are done. Plan: `docs/plans/avdtune.md`, sections 1a and 1b.

1. **First-run questions** (identity model, domain controller, profiles, network, optionally the client ID of an existing app registration). The tenant is not asked: it comes from the sign-in (step 2). A saved tenant is shown with a box "Forget the saved tenant"; that is the only way to change it (change log), and the next sign-in sets it again. An `environment.json` of an earlier version with a typed-in tenant (GUID or domain) stays valid. Saved in `C:\ProgramData\AVDTune\environment.json`, never a secret. The answers decide what follows: no domain controller means no domain step (groups come from Microsoft Entra ID); no FSLogix hides the FSLogix and App Masking pages. A later change goes into the change log.
2. **Microsoft 365 and Azure sign-in.** One normal Microsoft sign-in in the embedded window of the shared module (`Invoke-PackTuneBrowserSignIn`, authorization code with PKCE); the administrator signs in himself. Keevault is not used: AVDTune calls no Keevault function and fills in no password (`Tests\Check-Start.ps1` checks it). The refresh token gives three access tokens: Graph, Sites (both Microsoft Graph) and Arm (Azure Resource Manager). Microsoft's v2 tokens carry every consented scope of their resource, so the Graph and the Sites token both carry all Graph permissions of the table below; the separation is between Graph and Azure Resource Manager, not between the two Graph tokens. A token with a permission beyond the table is kept and named as a warning in the protocol. Tokens are kept in memory as SecureStrings, never written, removed when the window closes and by "Sign out". The sign-in window leaves a temporary profile with Microsoft cookies (`PackTuneSignIn-*` in the administrator's `%TEMP%`); AVDTune deletes it after the sign-in and on sign out, with retries. `Test-AVDTuneSessionClear` checks both (no token, no profile) before seal.
   **Tenant and app registration from the sign-in** (`Invoke-AVDTuneStartSignIn`). The form has an optional field for the account (name@domain), sent as `login_hint`.
   - No client ID: AVDTune sets up its own app registration first (`Install-AVDTuneAppRegistration`, after a confirmation). An administrator signs in through Microsoft's public client "Microsoft Graph Command Line Tools" (`14d82eec-204b-4c2f-b7e8-296a70dab67e`) at the authority `organizations` with `Application.ReadWrite.All`, `DelegatedPermissionGrant.ReadWrite.All` and `User.Read`; the `tid` of that token is the tenant. Through Microsoft Graph (`https://graph.microsoft.com/v1.0` only, adapter with a fake in the checks) AVDTune finds the registration `AVDTune` (name, tag `AVDTune`, redirect `http://localhost`, and the signed-in account is its only owner; anyone may name an app like that) or creates it: public client, redirect `http://localhost`, single tenant, tag and note, the delegated permissions of the table below, no secret, no certificate. Then the service principal (retried while Graph does not know the new registration yet; Azure Service Management gets its service principal when the tenant has none) and the admin consent (`oauth2PermissionGrant`, `AllPrincipals`, one per resource). Tenant and client ID go into `environment.json` (change log), then the normal sign-in with the new app follows (a second window; the account of the setup is the login hint). Roles: Application Administrator or Cloud Application Administrator for the registration, Privileged Role Administrator (or Global Administrator) for the consent; a 403 names the step and these roles. The consent the setup gives "Microsoft Graph Command Line Tools" stays in the tenant; the confirmation and the protocol say how to remove it (Entra admin center > Enterprise applications > Microsoft Graph Command Line Tools > Permissions > Revoke, or `Remove-MgOauth2PermissionGrant`).
   - Client ID entered by hand (stays possible), no tenant yet: with an account AVDTune reads the tenant of its domain from Microsoft's OpenID configuration (`https://login.microsoftonline.com/<domain>/v2.0/.well-known/openid-configuration`, the GUID in `issuer`; only that host, HTTPS, no redirects; the domain is checked strictly before any request) and signs in at that tenant. Without an account, or when the discovery fails, the sign-in goes to `organizations`, which only a multi-tenant registration accepts (AADSTS50194 gets a readable message).
   - After every sign-in the `tid` of the token is saved as the tenant ("Tenant taken from the sign-in", change log); it must match the tenant of the discovery. With a saved tenant the sign-in goes to that tenant and the `tid` must match; otherwise the message names both tenants and points to the first-run questions. A saved domain (older file) is replaced by the GUID of the sign-in.
3. **Domain controller** (only with a domain controller). IP or name and a domain account; LDAPS 636 first. The first contact shows the certificate (SHA-256 and SHA-1 thumbprint) and sends nothing until it is pinned for this environment. A changed certificate stops the connection (no fallback); replacing a pin is a separate confirmed action in the change log. The first contact also shows, as extra facts, whether Windows trusts the certificate chain and whether the name matches. LDAP 389 is never used silently: only when 636 does not answer, the server was never seen with LDAPS, and the administrator confirmed a clear warning in the window for exactly that server (a changed server name drops the confirmation; it goes into the protocol; without it nothing is sent). With a DNS name the bind over 389 is Kerberos only (NTLM refused); with an IP address it can only be NTLM, which does not authenticate the server (relay, offline cracking), and the warning says so. Signing and sealing always. A simple bind in clear text does not exist in the code. AVDTune reads RootDSE (DNS name, NetBIOS name, naming contexts, functional levels), the site of the DC, the OU tree and groups with their SIDs. The password stays in a SecureString and is cleared after the read.
4. **Snapshot gate.** The VM finds itself through the instance metadata service (subscription, resource group, VM, OS disk). "Create snapshot now" makes an incremental snapshot named by the pattern of the environment (`environment.json`, `Snapshot.NamePattern`, set in the first-run questions; default `{OsDisk}-{DD}.{MM}.{YYYY}-{N}`, `{N}` = next free number of that day; tokens `{OsDisk}` `{VM}` `{ImageVersion}` `{YYYY}` `{MM}` `{DD}` `{N}`) with tags ImageVersion, CreatedBy and CreatedWith=AVDTune. A snapshot counts only when it is finished and newer than the last change AVDTune made on the master (last Apply/Undo with a change: `state.json` `LastChange`, run records, automatic change log entries); before any change every finished snapshot of the OS disk counts. Because the snapshot time comes from Azure and the last change from the clock of the VM, the snapshot must be at least 10 minutes newer than the last change (a VM clock that runs behind cannot make an earlier snapshot count). It is confirmed by typing first and last name (two words, not matched against the sign-in, because shared admin accounts are used). The typed name, the signed-in Microsoft account and the local Windows account, time, snapshot ID and "created by AVDTune: yes/no" go into the protocol, the change log and `state.json` (`SnapshotGate`). The engine refuses every change of the master (Apply and Undo, not dry runs) until the gate is open; it is held in memory only, so every start begins closed.

## Permissions of the app registration

AVDTune has its own app registration `AVDTune` (not PackTune's), created at the first sign-in when the first-run questions name no client ID (public client, redirect `http://localhost`, no secret). A registration entered by hand needs the same. These delegated permissions need admin consent (the setup grants them; it also adds `openid` and `profile`, which the sign-in asks for):

| Token | Resource | Delegated permissions |
|---|---|---|
| Graph | Microsoft Graph | `Group.Read.All`, `DeviceManagementApps.Read.All` |
| Sites | Microsoft Graph | `Sites.Selected` (plus the one-time site grant as in PackTune) |
| Arm | Azure Service Management (`797f4846-ba00-4fd7-ba43-dac1f8f63013`) | `user_impersonation` |

`offline_access` is needed for the refresh token. `Group.ReadWrite.All` (Entra groups) comes in phase 3 and only for that action. In Azure the signed-in account needs, on the resource group of the VM, a role with `Microsoft.Compute/snapshots/read` and `write` and `Microsoft.Compute/disks/read` (for example Disk Snapshot Contributor on the resource group, plus Reader on the disk). A missing role or consent is named in the message.

The embedded sign-in loads the WebView2 SDK, downloaded once from NuGet by the shared module into `C:\ProgramData\AVDTune\WebView2` (Administrators and SYSTEM only). The shared module pins one SDK version and the SHA-256 of the package and of the three DLLs, and checks signature (Microsoft Corporation), pinned hash and write permissions on every load; a cache that fails is removed. AVDTune keeps no second signature or hash check. It adds only what the shared module does not look at (`Modules\AVDTune.Trust.psm1`, before every sign-in): the folder holds only the three SDK files and the marker `webview2-sdk.json`, no other file (side loading), no sub folder, no link; anything else is deleted (a link itself, never its target) and the pinned SDK is downloaded again; if it cannot be deleted the sign-in stops. At every start AVDTune also checks the whole state folder `C:\ProgramData\AVDTune` (owner Administrators or SYSTEM, no explicit rights for anyone else, no junctions or links, root protected with Administrators and SYSTEM only). A new folder is created in one step together with its protected ACL. A folder that someone prepared is never repaired in place (a recursive `icacls` as administrator would follow junctions): it is renamed to `AVDTune.untrusted-<yyyyMMdd-HHmmss>` (only the owner of its root is changed), its content is not read or taken over, a new folder is created and the first run starts again; the protocol, `logs\security.log` and a dialog tell the administrator. If that does not succeed in three tries, AVDTune does not start.

## Checks

`Tests\Check-Start.ps1` runs the whole sequence against fakes (`Tests\Fakes\FakeServices.ps1`): no network, 403 (missing role), consent missing, tenant mismatch, tenant discovery (found, invalid domain, network error, unknown domain, foreign issuer, tid differs), an older `environment.json` with a tenant, the own app registration (created, reused, someone else's not reused, missing roles, retries), changed LDAPS certificate, no downgrade of a pinned DC, LDAPS blocked without confirmation, planted WebView2 DLLs, snapshot older than the last change, one-word name, snapshot that fails. `Tests\Check-AVDTune.ps1` covers the state folder prepared by someone else and AVDTUNE_ROOT without AVDTUNE_FAKE. `Tests\Invoke-GuiSmoke.ps1` drives the window through all four stages and writes screenshots.
