# Office page (phase 6, issue 35)

Microsoft 365 Apps on the Golden Master with the Office Deployment Tool (ODT). Code: `Modules\AVDTune.Office.psm1`, page `AVDTune-Office.ps1`, checks `Tests\Check-Office.ps1` with `Tests\Fakes\FakeOffice.ps1`. Language and region and the VDI components follow in their own branches of the same issue.

## What it does
- Form (issue 61): channel, 32/64 bit, **licence**, **Outlook**, **languages** (ticks), **Install** (ticks), RemoveMSI. Fixed and not changeable: `SharedComputerLicensing = 1` and `Updates Enabled = FALSE` (multi-session needs both). Defaults: the sample of the AVD article (Monthly Enterprise, 64 bit, en-US + MatchOS) with the best-practice apps below.
- **Licence** replaces the product ID: *Microsoft 365 E3/E5 (Apps for enterprise)* = `O365ProPlusRetail` and *Microsoft 365 Business Premium (Apps for business)* = `O365BusinessRetail` (the two products that Windows multi-session supports, AVD article). "Retail" is only the Click-to-Run name. The state list shows the installed product in these terms. Business Premium is the only business plan with shared computer activation (Learn, shared computer activation).
- **Languages**: MatchOS plus 18 common ones (de-DE, en-US, en-GB, fr-FR, it-IT, es-ES, nl-NL, pl-PL, pt-PT, pt-BR, sv-SE, da-DK, nb-NO, fi-FI, cs-CZ, tr-TR, ja-JP, zh-CN); preselected MatchOS + en-US. The first `Language` element sets the shell UI language (Learn, ODT options), so the ticked IDs are written in list order with en-US first and MatchOS last (as in the sample of the AVD article). A valid language ID in a saved file that the list does not offer is still shown and kept.
- **Install** (ticks) instead of "Excluded apps": Word, Excel, PowerPoint and OneNote are preselected (best practice for a multi-user host: what users need, nothing that adds size, background tasks or support cases). Offered but off: Access, Publisher (Microsoft is retiring it), Groove (the old OneDrive sync client), Lync (Skype for Business, which the AVD article says AVD does not support) and Bing. Internally the config keeps `ExcludeApps`: every offered app that is not ticked, plus `OneDrive` and `Teams`, which are never ticks and always excluded because they come as their own VDI packages (#56, the AVD article installs OneDrive per machine and Teams with its own article). `Bing` is accepted as an ExcludeApp ID by the ODT but is not in the list of the Learn page (not verified).
- **Outlook** (own choice, not a tick; stored as `Outlook` = `both` | `classic` | `new`): classic = ODT app `Outlook`, new = ODT app `OutlookForWindows`. The configuration.xml excludes the one that is not chosen; `Outlook` and `OutlookForWindows` are not allowed in `ExcludeApps`. A config or undo record saved before issue 61 (no `Outlook`) is converted when it is read: one of the two excluded gives the other choice, none gives `both`, both excluded stays invalid.
- Preview of the exact `configuration.xml`. It is built with `XmlWriter` from validated values only (strict types, language regex with timeout, app and channel allow lists); a saved `config\office.json` that is not valid is refused (fail closed).
- Test: rows for installed state, channel, bit, licence, shared activation, update setting, languages, update UI policies, Windows edition. Read only. A row that is **red** and has a one-click fix shows a **Fix** button (see below); no other row has one.
- Install or reconfigure, remove, undo: behind the write gate; run record, `LastChange` (also on failure), change log entry (Added/Changed/Removed, failures as Note). Undo uses the state found before the first change (`config\office-undo.json`, never overwritten, deleted by the call that wrote it when that run failed without effect (no page, no link, download, signature, protection, unpack, contents), and otherwise only by a successful undo; read with types, `BeforeInstalled` must be a real boolean): remove when Office was not there, the earlier configuration when AVDTune knows it, otherwise no undo (says why). `LastChange` is set only when something is about to change, not for the early analysis exits (nothing to remove, invalid configuration).
- Remove uses `<Remove All="TRUE"/>`: it takes every Click-to-Run product off the master, not only the one of the form. The confirmation names every product found (`ProductReleaseIds`). The button is "Remove all Office products".
- Before Undo, the current state is compared with what AVDTune applied (product, channel, bit): if Office is installed differently now, Undo asks first (GUI: confirmation; module: `OFFICE-DRIFT` error unless `-AcceptDrift`). Limits of Undo (shown before it runs; the button is "Back to saved configuration"): it installs the saved earlier configuration (product, channel, bit) again, so the build is the current one of the channel, not the earlier build; languages that were installed but are not in the saved configuration and Office versions that RemoveMSI removed do not come back.
- "Set update policies": the two HKLM values `hideupdatenotifications` and `hideenabledisableupdates` of the AVD article as steps with Test/Apply/Undo (earlier value kept together with its registry type read through `RegGetRaw` (`GetValueKind`, `DoNotExpandEnvironmentNames`: REG_EXPAND_SZ keeps kind and raw text; UInt32 is a DWord stored as the Int32 with the same bits; other kinds refuse); the record is read with types, `LastChange` is set before the undo attempt and also when a step fails).

## One-click fixes on red rows (issue 61)
Two red rows can be fixed without an ODT run, each as a step with Test/Apply/Undo through the write gate (`Set-AVDTuneOfficeFix` / `Undo-AVDTuneOfficeFix`; run record, `LastChange` also on failure, change log entry category Office, undo record `config\office-fix-<name>-undo.json` written once with the earlier value and its registry type, typed read, deleted only by a successful undo). The page asks first (dry run, then the confirmation text of `Get-AVDTuneOfficeFixText`); "Undo one-click fixes" puts the earlier values back.
- **Shared Computer Activation** (`shared`): `HKLM\SOFTWARE\Microsoft\Office\ClickToRun\Configuration`, `SharedComputerLicensing`, REG_SZ `1`. Documented by Learn (shared computer activation, "Option 2: Use Registry Editor"): the device must be restarted, and a user who activated Office before needs the activation reset. The Group Policy way ("Use shared computer activation") is documented as well but not available for Apps for business, so the registry value is the one used for both licences. The row turns green when the value is `1`; the restart is only noted, not checked. Undo does not restart and does not restore reset activations (said in the confirmation).
- **Automatic updates** (`updates`): policy `HKLM\SOFTWARE\Policies\Microsoft\office\16.0\common\officeupdate`, `enableautomaticupdates`, REG_DWORD `0` (Group Policy "Enable automatic updates"). Learn names the Group Policy setting and says that the policy overrides the ODT setting; the registry value name is from Microsoft KB 2753538 and is the one the update block already writes (`updateblock.office-auto`). The row is green when the policy is `0` (even if the ODT value says TRUE) and red when the policy is `1`. A reconfigure with the ODT (`Updates Enabled = FALSE`) stays the other way.
- Without a fix: not installed, an unsupported product, channel/bit/language differences (they need a reconfigure, the Install button).
- The update block writes the same policy. Undo of the `updates` fix does not touch the value while the update block has settings in place (On or Partial) or a maintenance mode is active: it only discards the fix record, writes a change log note "value now belongs to the update block" and says so in the result. An Office install or reconfigure discards the fix records (change log note); an Undo refuses a record older than `config\office-applied.json`. A fix only accepts the registry type of its own value for the earlier value (`updates`: DWord, `shared`: String); key and name always come from the fix, never from the record. OneDrive and Teams stay in `ExcludeApps` in every configuration.

## Outlook recommendation for AVD and multi-session
- Microsoft's position (Learn, deployment of new Outlook): new Microsoft 365 deployments from version 2502 include the new Outlook by default and Microsoft encourages running classic and new side by side; side by side is recommended for organisations that rely on full .pst support or on features that still use classic Outlook libraries (mail merge in Word, people picker, @ mentions, people cards, Share to in Windows). That is why the page preselects **both**.
- New Outlook in VDI (Learn, "Deploy the new Outlook for Windows on VDI"): Windows 10 2004+ or Windows Server 2022+ (not Server 2019/2016), WebView2 current, .NET Framework 4.7.2+, AVD client Windows App 2.0.285.0 or newer; the new Outlook is installed as an MSIX package and ships with Windows 11 24H2. For all users of a machine the MSIX is provisioned (`Add-AppxProvisionedPackage`, or `Setup.exe --provision true`, Learn: deployment of new Outlook); user data lives in `%LocalAppData%\Packages\Microsoft.OutlookForWindows_8wekyb3d8bbwe` and `%LocalAppData%\Microsoft\olk`, and FSLogix supports roaming it (roadmap item RM473803, launched July 2025). When `AllowAllTrustedApps` is disabled the installation fails.
- Choose **classic only** when users depend on .pst files, COM add-ins or the Word/Office integrations above; **new only** when all users are on Exchange Online or supported accounts and need no classic-only feature; **both** for a gradual move (default, Microsoft's recommendation).
- **Not verified, for the test VM:** whether the ODT's `OutlookForWindows` app registers the new Outlook for every user of a multi-session host (versus provisioning with the standalone installer), and how it behaves with shared computer activation and FSLogix profiles. The page says so in its hint.

## Where the ODT comes from
1. Page `https://www.microsoft.com/en-us/download/details.aspx?id=49117` (host `www.microsoft.com`, no redirect followed, size limit).
2. Escaped slashes of a JSON text on the page (`https:\/\/...`, `\u002F`) are unescaped first. Then exactly one link `https://download.microsoft.com/download/<guid>/officedeploymenttool_<build>-<build>.exe` is taken from it (every candidate on download.microsoft.com is matched against the whole pattern: https, host, default port, no user info, no query, nothing behind `.exe`); none or several = stop.
3. Download into a new folder below the protected state folder (`temp\office-<guid>`, Administrators/SYSTEM only, checked before the download), `CreateNew`, size limit, no redirect.
4. Authenticode of the package (subject O and CN `Microsoft Corporation`, issuer Microsoft code signing CA, original file name `officedeploymenttool.exe` or `officedeploymenttool_<build>-<build>.exe`, nothing more), then `/quiet /extract:<folder>`.
5. The unpacked folder `odt` is checked like the work folder (admin-only). `setup.exe` by full path in it (no link) is held open with read share only from the first check until its process has ended (nobody can write to it, delete it or rename it in between); the folder must hold exactly `setup.exe` and `configuration-*.xml` (else stop, `BadContents`); Authenticode with exact subject, issuer, original file name `setup.exe`, file version major 16, and ProductName/FileDescription (its own trust key `odt-setup`, not a generic `setup.exe` in the shared list), checked again directly before the start. **ProductName and FileDescription are placeholders** (`Microsoft Office` / `Microsoft Office Deployment Tool`, compared exactly, case-sensitive, `\z`) until #17 delivers the real values from a real ODT; a wrong guess fails closed. Started without shell, no window, in a job object (timeout ends the tree). The folder is removed at the end.
